## 1. Резюме продукта

Универсальное приложение для OpenWrt, которое даёт **понятный веб-интерфейс** для управления VPN-подключением на уровне роутера вместо ручной правки YAML-конфига mihomo.

Что оно делает:
- принимает **несколько подписок** (Remnawave и любой совместимый бэкенд) и **ручные прокси** в единый пул серверов;
- отправляет **HWID-заголовки** по стандарту Happ/Remnawave, чтобы подписки с лимитом устройств работали;
- даёт **гибкую маршрутизацию**: разные сайты, категории и устройства домашней сети → разные серверы одновременно, с готовыми шаблонами для быстрого старта;
- показывает **квоты/срок подписок** и статус;
- встраивает **metacubexd** для детального мониторинга трафика/соединений/логов;
- генерирует профиль mihomo и управляет им через **nikki** (транспорт, TUN, DNS — остаются на nikki).

Кто пользователь: сам заказчик, семья/друзья без техбэкграунда, потенциально клиенты VPN-сервисов на Remnawave. В v1 — **один уровень доступа** (админ).

Чем НЕ является: не панель управления VPN-сервисом, не биллинг, не замена nikki/mihomo, не мультиплатформенный клиент.

## 3. Функциональные требования

### FR-1. Источники серверов

- **FR-1.1** Добавление подписки: имя, URL, интервал автообновления (по умолчанию из заголовка `profile-update-interval`, иначе 12 ч), включена/выключена.
- **FR-1.2** Несколько подписок активны **одновременно**; серверы из всех попадают в единый пул.
- **FR-1.3** Ручное добавление сервера: вставкой ссылки (`vless://`, `trojan://`, `ss://`, `vmess://`, `hysteria2://`, `tuic://`) или через форму (тип + поля). Использовать конвертер mihomo (`github.com/metacubex/mihomo/common/convert`), не писать свой парсер.
- **FR-1.4** Обновление подписки вручную кнопкой и по расписанию. Обновление **не сбрасывает** маршруты (FR-4.8).
- **FR-1.5** Удаление источника: показать, какие маршруты потеряют цель, предложить переназначить или удалить.
- **FR-1.6** Для каждой подписки показывать: статус последнего обновления, ошибку (человеческим языком), количество серверов, квоту трафика и срок действия (FR-7).

### FR-2. HWID (по спецификации Remnawave / стандарт Happ)

- **FR-2.1** Генерация HWID один раз, персистентно. Формат должен соответствовать `^[a-zA-Z0-9=-]{10,64}$`.  
  **Алгоритм:** `HEX_UPPER(SHA256(primary_lan_mac || random_salt_32B))[0:32]`. Соль генерируется один раз и хранится вместе с HWID. Hex выбран потому, что base64 содержит запрещённые символы (`+`, `/`, `_`).
- **FR-2.2** Хранение: `/etc/wellboard/hwid` (0600). Путь добавляется в `/lib/upgrade/keep.d/wellboard`, чтобы HWID **переживал sysupgrade** (иначе каждая перепрошивка занимает слот устройства в панели).
- **FR-2.3** При каждом запросе подписки отправлять заголовки:
  - `x-hwid: <hwid>` — обязательно;
  - `x-device-os: OpenWrt`, `x-ver-os: <версия из /etc/openwrt_release>`, `x-device-model: <из /etc/board.json>`, `user-agent: <см. 5.7>` — опционально.
- **FR-2.4** Читать ответные заголовки и показывать понятный статус подписки:
  - `x-hwid-active: true` → «Лимит устройств включён»;
  - `x-hwid-not-supported: true` → «Сервер не получил HWID» (это наш баг — логировать как ошибку);
  - `x-hwid-max-devices-reached: true` или `x-hwid-limit: true` → «Достигнут лимит устройств на подписке. Удалите лишнее устройство в личном кабинете»;
  - HTTP 404 при включённом HWID → та же подсказка + «проверьте, что ссылка актуальна».
- **FR-2.5** Экран «Настройки → Устройство»: показать HWID, кнопка «Сгенерировать заново» с предупреждением (займёт новый слот в панели).

### FR-3. Пул серверов и группы

- **FR-3.1** Единый список серверов: имя, источник, тип, страна (по флагу/emoji в имени или по гео IP — опционально), последняя измеренная задержка.
- **FR-3.2** Тест задержки по одному серверу и по всем (через mihomo API `/proxies/{name}/delay`).
- **FR-3.3** Пользовательские группы: имя, тип (`select` — ручной выбор, `url-test` — авто по задержке, `fallback` — по порядку, `load-balance`), список серверов. Группа может быть целью маршрута.
- **FR-3.4** Стабильные внутренние идентификаторы (`srv_xxx`, `grp_xxx`); отображаемые имена могут меняться, ссылки в маршрутах не ломаются.

### FR-4. Маршрутизация (ядро продукта)

- **FR-4.1** Маршрут = упорядоченный набор **условий** + **цель** + опции.
- **FR-4.2** Типы условий: `domain`, `domain-suffix`, `domain-keyword`, `geosite:<категория>`, `geoip:<страна>`, `ip-cidr`, `src-device` (устройство LAN), `dst-port`.  
  ❌ Нет условия «приложение/процесс» — на роутере mihomo не видит процессов клиентов. В UI объяснить это одним предложением в подсказке.
- **FR-4.3** Цели: конкретный сервер, группа, `DIRECT`, `REJECT`.
- **FR-4.4** Устройства LAN: список из DHCP-лизов (`/tmp/dhcp.leases`, ubus `dhcp`) с именем/MAC/IP. При назначении устройства в маршрут предлагать **закрепить статический лиз** (UCI `dhcp`), т.к. mihomo матчит по IP (`SRC-IP-CIDR`), а не по MAC. Без закрепления — предупреждение.
- **FR-4.5** Порядок маршрутов задаётся пользователем (drag-and-drop или стрелки) и однозначно транслируется в порядок `rules:` mihomo.
- **FR-4.6** Политика по умолчанию (для `MATCH`): `DIRECT` | сервер | группа. Глобальная настройка.
- **FR-4.7** Опция маршрута «если цель недоступна»: `блокировать` (по умолчанию) | `напрямую`. Реализация: генерировать служебную `fallback`-группу `[цель, REJECT]` или `[цель, DIRECT]`.
- **FR-4.8** Маршруты ссылаются на серверы/группы по ID. Если после обновления подписки сервер исчез — маршрут помечается «цель потеряна», не применяется молча, пользователю показывается предупреждение и предложение переназначить.
- **FR-4.9** Просмотр итогового результата: «Показать сгенерированный конфиг» (read-only, для отладки).

### FR-5. Шаблоны правил

- **FR-5.1** Каталог готовых шаблонов (см. Приложение В): каждый шаблон = имя, описание, набор условий. Применение шаблона = создать маршрут с этими условиями и выбранной целью.
- **FR-5.2** Шаблоны можно комбинировать; после применения маршрут становится обычным и редактируется.
- **FR-5.3** Шаблоны хранятся в приложении как данные (`templates/*.yaml`), обновляются вместе с приложением.
- **FR-5.4** Геоданные: источник runetfreedom по умолчанию, MetaCubeX как альтернатива; конфигурируется. Для ключевых шаблонов — встроенные локальные `rule-provider` списки как запасной вариант, если геоданные недоступны.

### FR-6. Применение конфигурации

- **FR-6.1** Любое изменение → кнопка «Применить» (не автоприменение на каждый клик). Индикатор «есть неприменённые изменения».
- **FR-6.2** Перед применением: генерация профиля → валидация `mihomo -t -f <profile>` → только при успехе запись профиля и перезапуск nikki.
- **FR-6.3** Хранить последние N (=5) применённых профилей; кнопка «Откатить к предыдущему».
- **FR-6.4** Если после перезапуска nikki не поднялся за 15 с — автоматический откат к последнему рабочему профилю + уведомление в UI.
- **FR-6.5** Экспорт/импорт состояния приложения (JSON) для бэкапа и переноса на другой роутер. HWID **не** экспортируется по умолчанию (отдельная галочка с предупреждением).

### FR-7. Статус и квоты

- **FR-7.1** Главный экран: VPN включён/выключен (управление сервисом nikki), список подписок с прогресс-баром трафика (`subscription-userinfo: upload=;download=;total=;expire=`) и датой окончания, количество активных маршрутов, последние ошибки.
- **FR-7.2** Предупреждения: осталось < 10% трафика, до окончания < 3 дней, подписка не обновлялась > 3 интервалов.
- **FR-7.3** Показывать `announce` из заголовков подписки (сообщение от провайдера), если есть.

### FR-8. Мониторинг

- **FR-8.1** Вкладка «Мониторинг» = встроенный **metacubexd** (pure-panel режим), настроенный на `external-controller` mihomo с секретом.
- **FR-8.2** Статику metacubexd отдаёт наш бэкенд (вендорим релиз в пакет или скачиваем при установке — решение агента, зафиксировать в DECISIONS). Параметры подключения передавать через URL (`hostname/port/secret`), секрет — только для аутентифицированной сессии.
- **FR-8.3** Никакой доработки metacubexd в v1.

### FR-9. Настройки и служебное

- **FR-9.1** Настройки: порт UI, язык, источник геоданных, политика по умолчанию, интервал проверки задержек, секрет mihomo API (генерируется автоматически).
- **FR-9.2** Просмотр логов приложения (последние 500 строк) и nikki/mihomo (через `logread`).
- **FR-9.3** Пункт меню в LuCI «WellBoard» → открывает UI (минимальный `luci-app-wellboard` с одной страницей-редиректом или iframe).
- **FR-9.4** Диагностика: «Проверить nikki», «Проверить доступ к mihomo API», «Проверить геоданные» — с понятными результатами.

## 4. Нефункциональные требования

- **NFR-1 Ресурсы:** RSS бэкенда в покое ≤ 40 МБ; бинарник ≤ 20 МБ (со встроенным фронтендом, без metacubexd); нет CGO (кросс-компиляция на все архитектуры OpenWrt).
- **NFR-2 Безопасность:**
  - 2.1 UI слушает только на LAN-интерфейсах (по умолчанию `br-lan`), не на WAN.
  - 2.2 Аутентификация — пароль root через ubus `session login`; сессионная cookie `HttpOnly; SameSite=Strict`; таймаут 24 ч.
  - 2.3 Секреты (URL подписок, секрет API, HWID) — файлы 0600, каталог `/etc/wellboard` 0700.
  - 2.4 Защита от CSRF (токен в заголовке для мутирующих запросов).
  - 2.5 Нет внешней телеметрии. Единственные исходящие запросы — подписки, геоданные, тест задержки.
- **NFR-3 Надёжность:** атомарная запись состояния (tmp + rename); валидация конфигурации до применения; автооткат (FR-6.4).
- **NFR-4 Совместимость:** OpenWrt 23.05 / 24.10 / текущий snapshot (apk). Зафиксировать минимальные версии nikki и mihomo, с которыми тестировалось (в `docs/COMPATIBILITY.md`).
- **NFR-5 Работа без интернета:** UI открывается и показывает состояние даже если подписки недоступны; ошибки — не блокирующие.
- **NFR-6 i18n:** все строки UI через словари; RU и EN.
- **NFR-7 Мобильный UI:** основные экраны удобны на телефоне (ширина 360px).
- **NFR-8 Наблюдаемость:** структурированные логи (`level`, `component`, `msg`), уровень настраивается.

## 5. Архитектура

### 5.1 Компоненты

```
┌──────────────────────────── роутер (OpenWrt) ────────────────────────────┐
│                                                                          │
│  Браузер ──HTTP :8090──▶ wellboard (Go daemon, procd)                   │
│                           ├─ embedded SPA (Vue 3, go:embed)              │
│                           ├─ REST/JSON API  /api/v1/*                    │
│                           ├─ Store: /etc/wellboard/state.json          │
│                           ├─ Fetcher: подписки + HWID-заголовки         │
│                           ├─ Generator: state → profile.yaml (mihomo)   │
│                           ├─ NikkiAdapter: запись профиля, validate,    │
│                           │              restart, health, rollback      │
│                           ├─ Auth: ubus session login                   │
│                           └─ Static: /ui/metacubexd/*                    │
│                                     │                                    │
│                                     ▼                                    │
│                         nikki (init/uci/nft/tun/dns)                     │
│                                     │                                    │
│                                     ▼                                    │
│                         mihomo (ядро) ◀── external-controller :9090 ◀── metacubexd (iframe)
└──────────────────────────────────────────────────────────────────────────┘
```

### 5.2 Стек

| Слой | Выбор | Почему |
|---|---|---|
| Бэкенд | **Go 1.22+**, только stdlib + `gopkg.in/yaml.v3` + конвертер из `metacubex/mihomo` (как библиотека) | Один статический бинарник, кросс-компиляция, mihomo сам на Go |
| Хранилище | JSON-файл состояния с атомарной записью | Без SQLite/CGO; объёмы данных малы |
| Фронтенд | **Vue 3 + TypeScript + Vite + Pinia**, CSS — Tailwind (или UnoCSS) | Лёгкий, быстро собирается, агенту знаком |
| Планировщик | внутренний тикер Go | Не зависим от cron |
| Пакетирование | OpenWrt SDK в GitHub Actions → `.ipk` и `.apk`; procd init; UCI `/etc/config/wellboard` | Стандарт OpenWrt |
| Тесты | `go test`, golden-файлы, mock-сервер Remnawave, Vitest, Docker `openwrt/rootfs` smoke | Агент может прогонять без железа |

  },
  "sources": [
    {"id":"sub_a1","kind":"subscription","name":"WellDone","url":"https://…","enabled":true,
     "update_interval_sec":43200,"last_update":"…","last_error":null,

### 5.4 Генерация профиля mihomo

Правила генератора (детерминированно, покрыто golden-тестами):

1. `proxies:` — все включённые серверы из всех источников. Имя в конфиге = `"<display> [<source>]"`; при коллизии добавлять суффикс `#2`. Внутри приложения всё по ID.
2. `proxy-groups:`:
   - пользовательские группы (FR-3.3) как есть;
   - для каждого маршрута — служебная группа `rt:<id>`: если `on_unavailable=block` → `fallback: [цель, REJECT]`, если `direct` → `fallback: [цель, DIRECT]`. Так один маршрут = одна строка в `rules`, а поведение при падении — прозрачное.
   - `rt:default` для политики по умолчанию.
3. `rule-providers:` — для геоданных/локальных списков (формат `behavior: domain|ipcidr|classical`).
4. `rules:` — маршруты в порядке `order`; каждое условие → отдельная строка (`GEOSITE,youtube,rt:rt_1`, `SRC-IP-CIDR,…,rt:rt_2`, …); в конце `MATCH,rt:default`.
5. **Не генерировать** транспортные секции (`tun`, `dns`, `mixed-port`, `external-controller` и т.п.) — они принадлежат nikki (⚠ проверить: если nikki применяет наш файл как *профиль* и накладывает свой mixin, то так; если nikki ожидает полный конфиг — генерировать минимально необходимое и зафиксировать в DECISIONS).

### 5.5 Интеграция с nikki (⚠ всё проверить по исходникам)

Гипотезы, которые агент обязан верифицировать в Фазе 0:
- Профили хранятся в каталоге вида `/etc/nikki/profiles/`, выбор активного профиля — через UCI `/etc/config/nikki` (секция `config`/`profile`).
- Есть механизм `mixin` для наложения настроек поверх профиля (порты, TUN, DNS).
- Сервис: `/etc/init.d/nikki {start|stop|restart|status}`; рабочий каталог `/etc/nikki/run/`; там же лежит финальный `config.yaml`, который получает mihomo.
- `external-controller` и `secret` mihomo задаются nikki (в mixin/UCI) — WellBoard должен **читать** их оттуда, а не переопределять.
- Каталог UI (для metacubexd) у nikki уже может существовать (`/etc/nikki/run/ui`) — можно переиспользовать.

Контракт адаптера (`internal/nikki`):
```go
type Adapter interface {
    Detect() (Info, error)              // версии nikki/mihomo, пути, api addr/secret
    WriteProfile(name string, yaml []byte) (path string, err error)
    Validate(path string) error         // mihomo -t -f path
    Activate(name string) error         // выбрать профиль в UCI + restart
    Health(timeout time.Duration) error // API отвечает, сервис running
    LastGood() (name string, ok bool)
}
```
Плюс `DryRunAdapter` для разработки на x86 (пишет в temp-каталог, запускает локальный mihomo для validate).

### 5.6 HWID — см. FR-2. Реализация в `internal/hwid`: `Load()`, `Generate()`, `Reset()`; MAC берётся из `ubus call network.device status '{"name":"br-lan"}'` (⚠ проверить имя интерфейса на устройстве; fallback — первый не-loopback интерфейс).

### 5.7 Получение подписок (`internal/subscription`)

1. Запрос `GET <url>` с заголовками FR-2.3. `User-Agent` должен заставить Remnawave вернуть **формат mihomo/clash** — ⚠ проверить по исходникам панели (`remnawave/backend`, модуль subscription templates), какая подстрока UA выбирает шаблон mihomo. Пока: `WellBoard/<ver> mihomo`.
2. Обработка ответа:
   - YAML с `proxies:` → взять только `proxies` (свои `proxy-groups`/`rules` панели игнорируем — маршрутизацию делает WellBoard);
   - иначе, если тело — base64-список ссылок или plain-список ссылок → конвертер mihomo → `proxies`;
   - иначе — ошибка «Неизвестный формат подписки».
3. Заголовки: `subscription-userinfo`, `profile-update-interval`, `profile-title` (может быть `base64:`), `announce`, `x-hwid-*`.
4. Таймаут 20 с, до 2 повторов с backoff; ошибки сети не удаляют прежний список серверов.
5. Мержинг: серверы матчатся по `(source_id, name, server, port)`; исчезнувшие помечаются `stale` и удаляются после подтверждения или через 3 обновления; маршруты на них — «цель потеряна» (FR-4.8).

### 5.8 Аутентификация
`POST /api/v1/login {password}` → `ubus call session login {"username":"root","password":…}` (через `/var/run/ubus.sock` или CLI). Успех → своя сессия в памяти + cookie. В dev-режиме — пароль из переменной окружения.

### 5.9 Мониторинг
`/ui/metacubexd/` отдаётся бэкендом (только для аутентифицированных). Вкладка «Мониторинг» = iframe `/ui/metacubexd/?hostname=<lan-ip>&port=<api-port>&secret=<secret>`. Если API mihomo слушает только `127.0.0.1`, бэкенд проксирует `/api/mihomo/*` → `127.0.0.1:9090` и указывает iframe на себя (⚠ проверить, что metacubexd корректно работает через прокси-путь; WebSocket для трафика/логов должен проксироваться).

### 5.10 Dev-режим и стенды
- `wellboard --dev --state ./dev/state.json --mihomo ./bin/mihomo` — запуск на Linux/x86 без nikki (DryRunAdapter).
- `test/mock-remnawave/` — HTTP-сервер с фикстурами: нормальная подписка (YAML и base64), `404` без `x-hwid`, ответ с `x-hwid-max-devices-reached`, `subscription-userinfo`, `announce`.
- `test/openwrt-docker/` — образ `openwrt/rootfs`, установка пакета, старт procd, проверка `/api/v1/health`.

## 9. Правила работы агента (guardrails)

1. **Не выдумывать внутренности nikki/Remnawave/mihomo.** Любой факт о них — со ссылкой на исходник в DECISIONS.
2. Одна фаза — один PR; в описании PR: какие FR закрыты, как проверить.
3. Тесты обязательны: без зелёного CI фаза не закрыта.
4. Зависимости минимальны; **без CGO**; новая зависимость — запись в DECISIONS с обоснованием.
5. Секреты никогда не логируются (URL подписок маскировать до хоста).
6. Комментарии в коде и коммиты — на английском; UI и документация для пользователя — RU (+ EN).
7. Решения из раздела 2 утверждены заказчиком — не менять самовольно; если считаешь решение неверным — предложи заказчику с аргументами, но продолжай работу по утверждённому.
8. Не расширять scope (см. раздел «Вне рамок»). Идеи — в `docs/BACKLOG.md`.
9. При любой ошибке применения конфигурации приоритет — **не оставить роутер без интернета**: откат важнее новой функции.
